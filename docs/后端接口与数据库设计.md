# 华中农业大学 · 校园运动场馆预约系统
# 正式版后端接口与数据库设计（v1.0）

> 版本：v1.0（配套前端原型 原型 v1）
> 适用：把当前纯前端原型（`index.html` + `js/*.js`）迁移为「前端 + 后端 + 数据库」的正式系统
> 同目录交付物：`docs/schema.sql`（可直接执行的 MySQL 8 建表脚本）

---

## 0. 结论先行：要不要现在就迁后端

**建议：要迁，但分两步走，不要推倒重来。**

| 问题 | 现状（原型） | 不做后端的风险 |
| --- | --- | --- |
| 数据存放 | 浏览器 localStorage | 换电脑/清缓存就没了，同学之间看不见彼此的预约 |
| 防重复预约 | 前端 `js/store.js` 内存校验 | 两个人同时点同一时段，**必然超卖**（各存各的本地数据） |
| 登录态 | 本地假装登录 | 任何人改一行 JS 就能冒充别人、冒充管理员 |
| 通知/举报/组队 | 只有自己看得到 | 组队招募、通知、举报处理全部失效 |

**第 1 步（1~2 天）**：把「用户/认证/场馆/预约/审核」这 5 件事搬到服务端 —— 这一层是**必须**的，因为防超卖只能在服务端做。
**第 2 步（2~3 天）**：再搬「组队 / 交流中心 / 好友 / 举报」等社区功能。

原型的分层（数据层 `store.js` 与视图层 `views.js` 分离）就是为这一步准备的：**前端页面几乎不用改，只把 `js/store.js` 换成 `js/api.js`（方法名、返回结构保持一致，内部改成 fetch）**。详见第 8 章。

## 1. 总体架构

```
浏览器（现有静态 SPA：index.html + views.js + actions.js + app.js）
        │  HTTPS / JSON
        ▼
Nginx（反向代理、静态资源、限流、HTTPS 证书）
        │
        ▼
应用服务  Node.js 20 + TypeScript（Express 或 NestJS）
   ├── 认证模块（JWT / 角色 / 封禁状态）
   ├── 预约模块（时段可用性、防超卖、状态机）
   ├── 组队模块（申请/审批/满员转预约）
   ├── 社区模块（帖子/评论/点赞/收藏/举报）
   └── 管理模块（审核/通知/举报处理/统计）
        │
        ├── MySQL 8（主数据；唯一索引兜底防超卖）
        ├── Redis（可选：refresh token 白名单、限流计数、热点时段缓存）
        └── 对象存储 MinIO / 阿里云 OSS（头像图片，DB 只存 URL）
```

### 1.1 技术选型建议

| 方案 | 适用场景 | 说明 |
| --- | --- | --- |
| **Node.js 20 + TypeScript + Express**（推荐） | 与现有前端同语言、人手少、快速上线 | 前端同学可直接维护后端；生态成熟（Prisma/TypeORM） |
| Node.js + NestJS | 多人协作、要长期维护 | 自带模块化/依赖注入/校验管道，代码更规范，学习成本略高 |
| Spring Boot（Java） | 学校已有 Java 运维体系 | 稳定、监控完善，但需要前后端两套语言 |
| Django / FastAPI（Python） | 团队熟悉 Python、要接数据分析 | 管理后台（Django Admin）开箱即用 |

无论选哪个，**接口都按本文档的 HTTP/JSON 规范实现**，前端不受影响。

### 1.2 部署形态（推荐）

- 单机 Docker Compose：`nginx + api + mysql + redis + minio`，适合校内服务器起步
- 学生规模 3 万人、每日预约约 1000+ 人次，单台 4C8G 足够；选课/开学高峰期可横向扩 2 个 api 实例（无状态，靠 JWT）

## 3. 表结构明细

约定：全部字符集 `utf8mb4`；主键统一 `BIGINT UNSIGNED AUTO_INCREMENT`；时间统一 `created_at DATETIME` / `updated_at DATETIME`；逻辑删除用 `status` 字段，不做物理删除（举报取证需要）。

### 3.1 users（用户：学生 + 管理员）

| 字段 | 类型 | 约束/说明 |
| --- | --- | --- |
| `id` | BIGINT UNSIGNED | PK |
| `role` | ENUM('student','admin') | 普通用户 / 管理员，**登录入口不同** |
| `student_no` | VARCHAR(20) | 学号，学生必填；`UNIQUE`；管理员为 NULL |
| `login_name` | VARCHAR(32) | 登录名：学生=学号，管理员=admin；`UNIQUE` |
| `password_hash` | VARCHAR(255) | bcrypt(cost=10) 或 argon2id，**禁止明文/MD5** |
| `must_change_password` | TINYINT(1) | 初始管理员为 1，首次登录强制改密 |
| `status` | ENUM('normal','muted','banned') | 正常 / 禁止发帖 / 封禁（**封禁仍可预约**） |
| `status_reason` | VARCHAR(255) | 封禁/禁言原因（来自举报处理） |
| `name` | VARCHAR(32) | 姓名，注册必填（原型同款） |
| `gender` | ENUM('male','female','unknown') | 性别，默认 unknown |
| `age` | TINYINT UNSIGNED | 年龄 |
| `grade` | VARCHAR(16) | 年级，如 2021级 |
| `major` | VARCHAR(64) | 专业 |

| `hobbies` | VARCHAR(128) | 爱好 |
| `bio` | VARCHAR(255) | 个人介绍 |
| `avatar_url` | VARCHAR(255) | 头像（对象存储 URL） |
| `last_login_at` | DATETIME | 上次登录时间 |
| `created_at` / `updated_at` | DATETIME | |

索引：`UNIQUE(login_name)`、`UNIQUE(student_no)`、`KEY(status)`

- 学生注册：`name + studentNo + password`（原型一致），服务端校验学号 6~20 位数字、密码 ≥ 6 位、学号唯一

### 3.4 bookings（预约单）★ 核心表

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | BIGINT UNSIGNED | PK |
| `venue_id` | SMALLINT UNSIGNED | FK → venues.id |
| `venue_type_id` | SMALLINT UNSIGNED | 冗余，便于按场馆统计 |
| `book_date` | DATE | 预约日期 |
| `slot_index` | TINYINT UNSIGNED | 时段序号 0~13（0=08:00-09:00） |
| `slot_start` | TIME | 冗余，`08:00`，用于唯一索引与查询 |
| `slot_end` | TIME | `09:00` |
| `user_id` | BIGINT UNSIGNED | 预约人（组队预约时为队长） |
| `reason` | VARCHAR(255) | **预约理由（必填）**，管理员审核时展示 |
| `member_count` | TINYINT UNSIGNED | 同行成员人数（选填，**不做任何要求与限制**） |
| `status` | ENUM('pending','approved','rejected','cancelled','expired') | 状态机见第 5 章 |
| `team_id` | BIGINT UNSIGNED | 由组队转来的预约，关联 teams.id |
| `active_flag` | TINYINT GENERATED | **防超卖关键字段**：`IF(status IN ('pending','approved'),1,NULL)` |
| `reviewed_by` / `reviewed_at` | BIGINT / DATETIME | 审核管理员、审核时间 |
| `reject_reason` | VARCHAR(255) | 拒绝原因（会展示给申请人） |
| `cancel_reason` | VARCHAR(255) | 取消原因（用户或管理员） |
| `created_at` / `updated_at` | DATETIME | |

**索引（防超卖的三道锁）**

```sql
-- ① 同一场地 + 同一天 + 同一时段，只允许一条「生效中」预约 → 数据库层最终防线
UNIQUE KEY uk_slot (venue_id, book_date, slot_start, active_flag)
-- ② 同一用户同一天同一时段只能有一条预约（跨场馆互斥：直接预约、发起组队、加入队伍、提交组队预约都受此约束）
UNIQUE KEY uk_user_slot (user_id, book_date, slot_start, active_flag)
-- ③ 常用查询
KEY idx_status_date (status, book_date)
KEY idx_user_date (user_id, book_date)
```

> **为什么用 `active_flag` 而不是直接 `UNIQUE(venue_id, book_date, slot_start)`**：
> MySQL 唯一索引中 `NULL` 不参与去重，因此「已拒绝 / 已取消」的记录 `active_flag = NULL`，可无限条；
> 只有 `pending`/`approved` 的记录 `active_flag = 1`，天然互斥。
> PostgreSQL 等价写法：`CREATE UNIQUE INDEX uk_slot ON bookings (venue_id, book_date, slot_start) WHERE status IN ('pending','approved');`

**处理动作对用户状态的影响（与原型一致）**

| 动作 | users.status | 影响范围 |
| --- | --- | --- |
| `warn` 警告 | 不变 | 记录到审计日志，可给用户发一条站内提醒 |
| `remove_content` 删除违规内容 | 不变 | 帖子/评论置 `removed` |
| `mute` 禁止发帖 | `muted` | 不能发帖/评论，可点赞收藏、可预约 |
| `ban` 封禁账号 | `banned` | 不能发帖/评论/加好友，**仍可登录并预约场馆** |
| `unmute` 解除限制 | `normal` | 恢复全部权限 |

### 3.11 好友关系

**friend_requests**

| `id` / `from_user_id` / `to_user_id` / `status` ENUM('pending','accepted','rejected') / `created_at` / `acted_at` |
| --- |

索引：`UNIQUE(from_user_id, to_user_id)`（同一对用户只保留一条申请记录，状态复用；原型中「重复申请被拒」即此规则）

**friendships**（好友关系）

| `user_id` / `friend_id` / `created_at` | `PRIMARY KEY(user_id, friend_id)` |

## 4. 时段、可用性与并发控制

### 4.1 时段模型

- 时段**不建表**，由 `open_hour / close_hour / slot_minutes` 推导：08:00 起，每 60 分钟一段，共 14 段（`slot_index` 0~13）
- 前端展示的 `slot_index` 与服务端落库值**必须一致**，避免时区/边界歧义
- 查询、约束、索引全部使用 `book_date + slot_start`（`TIME` 类型），跨时区安全

### 4.2 可用性接口（一次拉整屏，替代原型逐格查询）

`GET /api/v1/venues/availability?venueTypeId=badminton&date=2026-10-12`

返回该场馆类型下**所有场地 × 所有时段**的状态矩阵（36 张球台 × 14 段 = 504 格，一次返回约 20KB，前端一次渲染）：

- `free` 可预约（绿）
- `mine` 我的预约（蓝）
- `pending` 已被他人提交待审核（橙）
- `taken` 已通过审核（灰）
- `past` 已过期时段（浅灰）
- `blocked` 场地维修/征用（新增状态）
- `conflict` 该时段你已预约了其他场馆（跨场馆互斥，需先取消原预约才能约此处；原型已实现）

### 4.3 「可预约日期」规则

允许预约的日期 = `本月内` ∩ `今天 ~ 今天 + days_ahead_limit`
（原型只做了「本月内」，正式版建议同时限天数，例如最多提前 7 天，避免热门时段被长期占满）
服务端在提交时**必须重新校验日期**，不能信任前端传值。

### 4.4 防超卖方案（三道锁 + 幂等）

| 层 | 手段 | 拦截的问题 |
| --- | --- | --- |
| ① 应用层 | 事务内先查可用性，给出友好提示 | 正常情况下的重复预约（返回 409 + 提示） |
| ② 数据库唯一索引 | `uk_slot(venue_id, book_date, slot_start, active_flag)` | **并发提交**（两请求同时通过①，只有一条能插入成功） |
| ③ 幂等键 | 请求头 `Idempotency-Key: <uuid>`，Redis 5 分钟内去重 | 用户双击、网络重试导致的重复下单 |

**跨场馆时段独占（原型已实现，正式版必须保留）**

同一用户在同一天、同一时段内**只能占用一个场馆**，覆盖四条入口：直接预约、发起组队、加入他人队伍、队长提交组队预约；队长同意入队前需再复核一次（防止申请人先申请、之后又在同时段预约了别的场馆）。

- 拦截后返回 `40905`，提示需带具体场馆与时段，例如「你在该时段已预约了其他场馆（羽毛球馆 羽01 11:00-12:00），需先取消该预约才能发起组队」
- 用户取消原预约后，该时段立即恢复可预约、可组队（无定时任务依赖）
- 可用性矩阵在该场地该时段本身空闲、但当前用户同日同时段另有生效预约时返回 `conflict`
- 数据库层由 `uk_user_slot` 兜底：组队提交后生成的预约同样写入 `bookings`，因此并发场景不会绕过这条规则

**推荐实现（伪代码，无需显式加锁）**

```
BEGIN;
  -- 1) 校验：场地启用、日期在允许范围、预约理由非空、用户状态/每日额度
  -- 2) 校验同一用户同时段无预约（uk_user_slot 也会兜底）
  -- 3) 插入预约单 + 成员名单
  INSERT INTO bookings (...) VALUES (...);   -- 命中 uk_slot 会直接抛 1062
  INSERT INTO booking_members (...) VALUES (...);
  -- 4) 写审计/日志
COMMIT;
-- 捕获 Duplicate entry 'uk_slot' → 返回 409 SLOT_TAKEN「该时段刚被其他同学预约，请选择其他时段」
```

> 选 `INSERT + 捕获唯一键冲突` 而不是 `SELECT ... FOR UPDATE`：代码更短、无死锁风险、依托数据库原子性。
> 若业务要求「候补队列」，则在冲突时把请求写入 `booking_waitlist`（可选扩展），有人取消时按队列顺序通知。

### 4.5 定时任务（建议 3 个）

| 任务 | 频率 | 作用 |
| --- | --- | --- |
| 过期预约归档 | 每日 00:05 | `book_date < 今天` 的 `approved` → `expired`，释放唯一键占位 |
| 组队过期关闭 | 每小时 | `expire_at < now()` 的 `teams` → `expired` |
| 待审核超时提醒 | 每小时 | 超过 24 小时未审核的预约提醒管理员（站内/邮件） |

## 5. 预约状态机

```
                 ┌──────────── 用户取消 ────────────┐
                 ▼                                  │
[创建] ──► pending ──管理员通过──► approved ────────┘（可取消）
              │                        │
              │                        └── 日期已过 ──► expired
              └──管理员拒绝──► rejected（附 reject_reason）
```

| 状态 | 是否占用时段（active_flag=1） | 用户可见操作 |
| --- | --- | --- |
| `pending` | 是 | 取消预约 |
| `approved` | 是 | 取消预约（建议：开始前 2 小时截止） |
| `rejected` | 否（NULL） | 查看拒绝原因，可另选时段重新预约 |
| `cancelled` | 否 | 仅历史记录 |
| `expired` | 否 | 仅历史记录 |

> **过期单的处理**：`book_date + slot_start` 已过去的预约，即使仍处于 `pending`，也会继续出现在管理员「待审核预约」列表中（置灰 + 标注「已过期」），但**不允许再审核**（通过/拒绝均返回 `409` 提示「该预约的活动时间已过，不能再审核」）。正式版建议由 §4.5 的定时任务将其统一置为 `expired` 并从待审队列移除。

**组队状态机**：`open（招募中）→ full（人数已满）→ booked（已生成预约，等待审核）`；未满则 `closed/expired`。
成员退出（`POST /teams/:id/leave`）后 `joined_count-1`，若队伍原为 `full` 则回到 `open`；队伍已 `booked` 时需队长先取消预约，成员才能退出。

**组队过期**：当 `book_date + slot_start` 已过去，该组队进入 `expired` 状态——交流中心「组队」页的卡片置灰并显示「已过期」，申请加入、同意/拒绝入队、退出队伍、提交预约全部拒绝（返回 `40901` 同款提示「该组队活动时间已过，不能再操作」）。

## 6. 认证与权限

### 6.1 登录方式（学生与管理员分流，与原型一致）

| 入口 | 接口 | 凭据 | 说明 |
| --- | --- | --- | --- |
| 学生登录 | `POST /api/v1/auth/login/student` | `studentNo` + `password` | 学号即登录名 |
| 管理员登录 | `POST /api/v1/auth/login/admin` | `loginName`（admin）+ `password` | 独立入口，普通账号无法登录该入口 |

### 6.2 令牌方案

- `access_token`：JWT，有效期 30 分钟，负载含 `uid / role / status`（**status 也要带**，便于快速拒绝已封禁用户的写操作）
- `refresh_token`：有效期 7 天，存 Redis 白名单（可主动踢下线），`POST /auth/refresh` 换新 access
- 传输：`Authorization: Bearer <access_token>`；若用 HttpOnly Cookie，则需额外加 CSRF Token
- 密码：bcrypt(cost=10) / argon2id；登录失败 5 次锁定 10 分钟（Redis 计数）

### 6.3 管理员首次登录强制改密

1. 登录成功但 `must_change_password=1` → 返回 `{ needChangePassword: true }`
2. 除 `POST /auth/password`、`GET /auth/me`、`POST /auth/logout` 外，其它接口一律返回 `403 / 40304 PASSWORD_CHANGE_REQUIRED`
3. 改密成功后 `must_change_password=0`，同时**吊销所有旧 refresh token**

### 9.2 提交预约

`POST /api/v1/bookings`（请求头带 `Idempotency-Key`）

```json
{
  "venueId": 101,
  "date": "2026-10-12",
  "slotIndex": 3,
  "reason": "院队训练",
  "members": ["张伟", "李娜", "王强", "陈静"]
}
```

成功：

```json
{ "code": 0, "message": "预约已提交，等待管理员审核",
  "data": { "bookingId": 9102, "status": "pending", "venueCode": "羽01", "slotLabel": "11:00 - 12:00" } }
```

未填预约理由（原型同样规则）：

```json
{ "code": 40902, "message": "请填写预约理由" }
```

并发抢到同一时段（由唯一索引 `uk_slot` 拦截）：

```json
{ "code": 40901, "message": "该时段刚被其他同学预约，请选择其他时段" }
```

### 9.3 组队满员转预约

`POST /api/v1/teams/55/book`（队长）

```json
{ "code": 0, "message": "已提交预约，等待管理员审核", "data": { "bookingId": 9103, "teamStatus": "booked" } }
```

失败示例：`{ "code": 42201, "message": "队伍人数未满（9/12），暂不能提交预约" }`

### 9.4 举报处理（封禁但仍可预约）

`POST /api/v1/admin/reports/31/resolve`

```json
{ "action": "ban", "note": "发布广告，封禁 7 天" }
```

响应：

```json
{ "code": 0, "data": { "reportId": 31, "status": "resolved", "action": "ban", "userStatus": "banned" } }
```

对应用户后续行为：`POST /posts` → `403 / 40303`；`POST /bookings` → **正常 200**（需求明确要求封号后仍可预约）。

## 11. 前端迁移方案（改动很小）

### 11.1 改造原则

原型已经分层，因此**视图层 `views.js` / 交互层 `actions.js` / 路由 `app.js` 基本不动**，只需替换数据来源。

| 原型文件 | 正式版处理 |
| --- | --- |
| `js/store.js` | 删除，替换为 `js/api.js`（保留同名方法，内部改 fetch） |
| `js/data.js` | 场馆与时段常量改为启动时从 `/venue-types` 拉取；本地只保留纯展示常量 |
| `js/views.js` / `js/actions.js` / `js/app.js` | 仅把同步调用改为 `await`（或加载态），其余不变 |
| `index.html` | 不变（仍可作静态资源部署） |

### 11.2 方法映射表
